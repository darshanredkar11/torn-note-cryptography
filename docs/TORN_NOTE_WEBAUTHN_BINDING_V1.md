# Torn Note + WebAuthn Binding Protocol — V1

**Status:** Proposed protocol specification for implementation and adversarial review  
**Protocol identifier:** `TORN_NOTE_WEBAUTHN_BINDING_V1`  
**Implementation target:** Java 21 business-identity-wallet reference application  
**Security status:** Research protocol; not production-ready or independently audited

This document defines how a WebAuthn authentication assertion and a Torn Note authorization are bound to the same immutable business transaction. It is intentionally a protocol document, not a claim that the current repository already implements WebAuthn.

## 1. Design objective

A verifier must not accept a valid WebAuthn assertion for transaction A together with a valid Torn Note authorization for transaction B.

Both proof systems must commit to one server-authoritative transaction digest:

`H_tx = SHA-256(UTF8("TORN-NOTE/transaction/v1\\0") || JCS(TransactionEnvelope))`

The WebAuthn ceremony is associated server-side with `H_tx` (and with the selected Torn Note authorization descriptor). The Torn Note signatures cover a domain-separated authorization message that includes the exact same `H_tx`.

The verifier independently validates both proof systems. Neither proof substitutes for the other.

### 1.1 V1 proof profile

For the first integration experiment, V1 is **additive**:

1. WebAuthn assertion from an active credential registered to the employee.
2. Existing Torn Note master/identity Ed25519 signature.
3. Torn Note factor-A Ed25519 signature.
4. Torn Note factor-B Ed25519 signature.

This deliberately retains the current Torn Note 3-of-3 semantics while adding a WebAuthn gate. The employee identity key and WebAuthn credential must both be enrolled to the same immutable `subjectId`; the note inventory must also be assigned to that subject.

This is a four-proof profile, not a claim that WebAuthn is mathematically equivalent to an Ed25519 signature over arbitrary application data. A later profile may evaluate using the WebAuthn credential as the identity/master proof and removing the separate master Ed25519 signature. That is a separate compatibility and threat-model decision and is **not** silently folded into V1.

## 2. Terms and identifiers

- **TransactionEnvelope:** immutable, server-authoritative description of the action and every security-relevant parameter.
- **`H_tx`:** SHA-256 digest of the canonical TransactionEnvelope, with transaction-domain separation.
- **InventoryManifestV1:** issuer-signed commitment to a finite note inventory and its intended tenant, owner, audience and action scope.
- **NoteAuthorizationEnvelope:** canonical description of the selected note and the transaction it authorizes.
- **`D_note`:** digest of the NoteAuthorizationEnvelope; all three Torn Note Ed25519 signatures cover this digest.
- **WebAuthn challenge:** fresh random 32-byte value generated by the relying party. It is not a deterministic encoding of `H_tx`; a server-side record binds it to the transaction.
- **Audience:** exact application/verifier identifier for which the authorization is valid. It is distinct from the WebAuthn RP ID.
- **Subject:** immutable internal employee/wallet identity identifier. Email address or display name is not a stable subject identifier.

All identifiers, timestamps, encodings, protocol versions and algorithm suites must have one unambiguous representation.

## 3. Canonical transaction and H_tx

### 3.1 Canonicalization

V1 adopts the JSON Canonicalization Scheme (JCS), RFC 8785, for JSON envelopes.

Implementations MUST:
- reject duplicate JSON property names before canonicalization;
- reject invalid Unicode and values outside the accepted I-JSON/JCS profile;
- apply the RFC 8785 serialization rules exactly, including property sorting and primitive serialization;
- preserve string code points as supplied; JCS does not perform Unicode normalization;
- represent monetary amounts and arbitrary-precision integers as decimal strings, not unsafe JavaScript floating-point numbers;
- use field-specific normalization rules for domain values (for example, currency codes and bank identifiers) **before** building the envelope;
- reject unknown security-critical schema versions rather than guessing how to interpret them.

Sorting Java map keys is not, by itself, a JCS implementation. The current demo's Jackson `ORDER_MAP_ENTRIES_BY_KEYS` setting must not be treated as proof of RFC 8785 compliance.

Reference: [RFC 8785 — JSON Canonicalization Scheme](https://www.rfc-editor.org/rfc/rfc8785.html).

### 3.2 TransactionEnvelope schema

The following is an illustrative shape. Each action type must define its required fields and validation rules.

```json
{
  "protocol": "TORN-NOTE-TX",
  "version": "1",
  "transactionId": "server-generated-unique-id",
  "tenantId": "company-123",
  "subjectId": "employee-456",
  "audience": "finance-approval-service",
  "action": "CHANGE_SUPPLIER_BANK_ACCOUNT",
  "resource": {
    "type": "supplier",
    "id": "supplier-789",
    "version": "17"
  },
  "actionData": {
    "beneficiaryVersionId": "beneficiary-789-v4",
    "destinationFingerprint": "base64url-encoded-commitment",
    "currency": "INR",
    "amountMinorUnits": "85000000"
  },
  "policyVersion": "supplier-bank-change-policy/3",
  "issuedAt": "2026-11-18T00:00:00Z",
  "expiresAt": "2026-11-18T00:02:00Z"
}
```

The values above are examples, not production account data or a finalized business schema.

The envelope MUST include, directly or by immutable versioned reference, every value that can change the action's meaning: tenant, subject, audience, action, resource, destination/beneficiary, amount and currency where applicable, relevant policy version, request identity, issue time and expiry. A verifier MUST resolve referenced business data by the exact immutable version committed by the envelope. It MUST NOT resolve a mutable alias such as “current supplier bank account” at execution time.

If a destination fingerprint is used, the business service must verify that it commits to the exact destination details that will be used. A hash is not encryption and must not be used as a privacy mechanism. Sensitive transaction fields must be protected in transit and at rest and excluded from ordinary logs.

### 3.3 H_tx calculation

Let `JCS(T)` be the exact UTF-8 bytes of the RFC 8785 canonical TransactionEnvelope.

```text
H_tx = SHA-256(
    UTF8("TORN-NOTE/transaction/v1\\0")
    || JCS(T)
)
```

`H_tx` is exactly 32 bytes. Its wire representation is unpadded base64url or lowercase hexadecimal, with the selected representation fixed by the API schema. Implementations must compare the decoded 32-byte values, not text with permissive normalization.

The verifier MUST load the authoritative transaction record using `transactionId`, revalidate its status and expiry, reconstruct the TransactionEnvelope, and recompute `H_tx`. A client-supplied digest is never authoritative.

## 4. Torn Note binding

### 4.1 Inventory manifest must bind ownership and scope

The current `InventoryManifest` commits to inventory ID, note count and Merkle root. That is sufficient for the current demo's inventory-integrity test, but it does not itself bind the inventory to a tenant, employee, audience or action scope.

V1 MUST extend the issuer-signed manifest (as a new versioned manifest type) to include at least:

- manifest protocol/version and algorithm suite;
- `inventoryId`, `noteCount` and 32-byte Merkle root;
- `tenantId` and `ownerSubjectId`;
- exact `audience`;
- allowed action identifiers or a defined action scope;
- `issuedAt` and `expiresAt`.

The verifier continues to pin the issuer public key independently. It MUST NOT trust a public key supplied by the manifest being verified. Manifest V0 bytes and verification rules must remain unchanged; do not silently reinterpret an existing V0 signature as V1.

### 4.2 NoteAuthorizationEnvelope

For a selected note, construct the following canonical object:

```json
{
  "protocol": "TORN-NOTE-AUTHZ",
  "version": "1",
  "suite": "ED25519-3OF3",
  "tenantId": "company-123",
  "subjectId": "employee-456",
  "audience": "finance-approval-service",
  "inventoryId": "finance-wallet-2026-Q4",
  "manifestRoot": "base64url-root",
  "noteId": "base64url-note-id",
  "factorAKey": "base64url-subject-public-key",
  "factorBKey": "base64url-subject-public-key",
  "transactionDigest": "base64url-H_tx"
}
```

The verifier MUST establish that:
- the manifest signature is valid under the independently pinned issuer key;
- the manifest tenant, subject, audience, action scope and validity window match the transaction;
- the note inventory ID matches the manifest;
- the note ID and factor public keys prove membership in the manifest's Merkle root;
- the selected note is not already spent;
- the master identity key and WebAuthn credential are both registered to the same `subjectId`;
- the NoteAuthorizationEnvelope's tenant, subject, audience and `H_tx` match the authoritative transaction.

### 4.3 D_note and Torn Note signatures

Let `JCS(N)` be the RFC 8785 canonical UTF-8 bytes of the NoteAuthorizationEnvelope.

```text
D_note = SHA-256(
    UTF8("TORN-NOTE/authorization/v1\\0")
    || JCS(N)
)

sigma_master = Ed25519.Sign(masterPrivateKey, D_note)
sigma_A      = Ed25519.Sign(noteFactorAPrivateKey, D_note)
sigma_B      = Ed25519.Sign(noteFactorBPrivateKey, D_note)
```

All three signatures cover the same `D_note`. Because `N` contains `H_tx`, the three Torn Note signatures are transitively bound to the exact transaction digest. The verifier recomputes `D_note` from trusted/validated inputs; it must not accept a client-supplied `D_note` as authoritative.

The leaf definition and proof encoding must also be versioned and unambiguous. V1 should use a canonical, length-delimited or canonical-object encoding for the leaf preimage, rather than relying on concatenation of arbitrary variable-length fields. Merkle leaf and internal-node domains must be distinct.

## 5. WebAuthn binding

### 5.1 Challenge creation

After the server has created and frozen the transaction and selected the note descriptor, it creates a fresh challenge:

```text
C = CSPRNG(32 bytes)
challengeHash = SHA-256(C)
```

The challenge is sent to the browser as unpadded base64url in WebAuthn `PublicKeyCredentialRequestOptions.challenge`.

The relying party persists a pending challenge record containing at least:

- `challengeHash`;
- `transactionId`, recomputed `H_tx` and `D_note`;
- `tenantId`, `subjectId` and `audience`;
- the allowed WebAuthn credential IDs (or a rigorously defined discoverable-credential policy);
- exact expected RP ID and allowed origin set;
- required user-verification policy;
- creation and expiry timestamps;
- status: `PENDING`, `CONSUMED` or `EXPIRED`.

The challenge is random and independent of `H_tx`. The server-side record is the binding between the challenge, the transaction and the selected Torn Note. Binding `D_note` as well as `H_tx` prevents a valid passkey assertion from being spliced onto a different note authorization for the same transaction.

Do not rely on a client-provided `transactionId`, digest or note descriptor without loading and validating the matching server-side pending record.

A short challenge lifetime is recommended (for example, two minutes, configurable by policy). Expiry is checked server-side. The browser's WebAuthn `timeout` is only a client hint and is not a substitute for server-side expiry.

### 5.2 Browser ceremony

The browser performs `navigator.credentials.get()` using the server-generated request options. V1 requires user verification for this high-impact business operation (`userVerification: "required"`). The resulting assertion is returned to the verifier over the authenticated application channel.

Reference: [W3C Web Authentication Level 3](https://www.w3.org/TR/webauthn-3/).

### 5.3 Assertion verification

Use a maintained WebAuthn server library. Do not hand-roll the WebAuthn parser or signature verification in the business application.

The server MUST validate, at minimum:

1. The credential ID is registered, active and associated with the expected `subjectId`.
2. `clientDataJSON.type` is `webauthn.get`.
3. The decoded `clientDataJSON.challenge` equals the exact 32-byte challenge represented by the stored `challengeHash`.
4. `clientDataJSON.origin` is an exact member of the configured origin allowlist. Do not use substring or suffix matching.
5. Cross-origin use is rejected unless a separately specified and tested embedding policy explicitly permits it.
6. `authenticatorData.rpIdHash` equals SHA-256 of the configured RP ID.
7. User-presence is set and user-verification is set, because V1 requests UV as required.
8. The assertion signature verifies over the WebAuthn-defined signed data using the public key stored at credential registration.
9. The credential and account have not been revoked, suspended or disabled.
10. If a user handle is returned, it matches the account/subject association. The credential ID to subject mapping remains authoritative.

The WebAuthn signature input is defined by WebAuthn (authenticator data concatenated with the hash of the original `clientDataJSON` bytes). Do not canonicalize or reserialize `clientDataJSON` before signature verification.

Signature-counter handling must follow the chosen library and authenticator policy. A zero counter can occur with synced/multi-device passkeys; zero alone must not be treated as proof of cloning. Counter anomalies are risk signals to handle according to policy, not a substitute for credential status and signature validation.

Registration is a separate prerequisite: verify the WebAuthn registration ceremony, store the credential public key and metadata, and bind that credential to the same immutable subject as the Torn Note master public key and inventory assignment.

## 6. What WebAuthn proves — and does not prove

A valid assertion proves that the registered authenticator produced an assertion for the relying party's fresh challenge, subject to the checks above. With UV required, the authenticator reports that its configured user-verification ceremony succeeded.

It does **not**, by itself, prove that the authenticator displayed or that the employee understood the supplier name, destination account, amount or other transaction details. Standard WebAuthn does not provide a trusted transaction display merely because the challenge is transaction-specific.

Therefore:
- the application must present the transaction details from the same immutable server-side transaction before initiating approval;
- the server must execute only the exact immutable transaction whose digest was bound into the challenge and note signatures;
- a compromised browser or application UI may still misrepresent what is shown to the user;
- a genuine “what you see is what you sign” claim requires a trusted display/approval path, such as a separately evaluated trusted device/app flow or an appropriately supported secure payment confirmation mechanism.

Do not market ordinary WebAuthn as a trusted display or transaction-signing screen.

## 7. End-to-end protocol flow

1. **Create transaction.** The business server validates the request, constructs an immutable TransactionEnvelope, stores it, and computes `H_tx`.
2. **Select note.** The wallet selects an unused note from an inventory assigned to the same tenant and subject.
3. **Build note descriptor.** The parties construct the NoteAuthorizationEnvelope and compute `D_note`.
4. **Create challenge.** The relying party generates random `C`, stores `SHA-256(C)` with `transactionId`, `H_tx`, `D_note`, subject, audience, RP ID, origin policy and expiry, then returns WebAuthn request options.
5. **WebAuthn assertion.** The authenticator returns a WebAuthn assertion for `C`.
6. **Torn Note authorization.** The wallet signs `D_note` with the master, factor-A and factor-B Ed25519 keys. The signatures may be created before or after the WebAuthn ceremony, but all must be tied to the same frozen `H_tx` and `D_note`.
7. **Verify.** The server reloads the transaction and challenge record, recomputes `H_tx` and `D_note`, validates the manifest and Merkle proof, verifies the three Ed25519 signatures, and verifies the WebAuthn assertion.
8. **Atomically authorize.** In one database transaction, consume the pending challenge, reserve/consume the note for this exact transaction, persist the authorization decision and insert a durable action/outbox record.
9. **Execute idempotently.** A worker executes the protected business action using the same immutable transaction and a stable idempotency key. The action result is reconciled and audited.

No protected side effect is allowed before step 8 commits.

## 8. Atomic replay protection and action execution

The current `InMemorySpendStore` is a demo/test adapter. Production must use a shared durable database with a unique constraint on `(inventory_id, note_id)`. The challenge must also be single-use with a conditional state transition.

Illustrative schema:

```sql
CREATE TABLE webauthn_challenge (
    challenge_hash  bytea       PRIMARY KEY,
    transaction_id  text        NOT NULL,
    tx_digest       bytea       NOT NULL,
    note_digest     bytea       NOT NULL,
    subject_id      text        NOT NULL,
    audience        text        NOT NULL,
    rp_id           text        NOT NULL,
    expires_at      timestamptz NOT NULL,
    status          text        NOT NULL,
    consumed_at     timestamptz
);

CREATE TABLE spent_note (
    inventory_id    text        NOT NULL,
    note_id         bytea       NOT NULL,
    transaction_id  text        NOT NULL,
    tx_digest       bytea       NOT NULL,
    consumed_at     timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (inventory_id, note_id)
);
```

The final authorization transaction must:
- conditionally change the matching unexpired challenge from `PENDING` to `CONSUMED`;
- insert the note spend record (or reserve record) with a uniqueness constraint;
- persist the authorization decision and exact `transactionId`/`H_tx`;
- insert an outbox item for the exact business operation;
- commit all of those changes together.

If any required insert/update fails, roll back the transaction and reject the authorization. Do not implement a read-then-write “is this note unused?” check.

For a business operation that is fully local to the same relational database, the spend record and business state change can be committed in the same database transaction.

For an external payment/banking API, the external side effect cannot be assumed to join our database transaction. Use a transactional outbox and a stable idempotency key (normally the immutable `transactionId`), and retry/reconcile with that same key and same payload. Once an authorization has been durably reserved for a transaction, never release the note automatically merely because the remote response timed out; the outcome may be unknown. Reconcile the external operation before any recovery action.

## 9. Required security and adversarial tests

The V1 integration is not complete until the test suite proves rejection of:

### Transaction binding / splicing
- WebAuthn assertion for transaction A paired with Torn Note signatures for transaction B.
- WebAuthn challenge for one `D_note` paired with a different note descriptor for the same `H_tx`.
- Changed amount, currency, beneficiary, supplier, tenant, subject, audience, resource version, policy version or expiry after authorization.
- A client-supplied `H_tx` that differs from the server recomputation.
- A valid digest with a different mutable business payload at execution time.
- A note inventory assigned to another subject, tenant, audience or action scope.

### WebAuthn
- Wrong or expired challenge; challenge replay; malformed base64url challenge.
- Wrong `type`, origin, RP ID hash, credential ID or subject association.
- Invalid authenticator signature.
- User-presence or required user-verification flag missing.
- Revoked/suspended credential.
- Cross-origin assertion where cross-origin is not allowed.
- Credential counter anomalies handled according to configured policy.

### Torn Note
- Invalid issuer signature or untrusted issuer key.
- Tampered manifest/root.
- Fabricated note or invalid Merkle proof.
- Missing/invalid master, factor-A or factor-B signature.
- Wrong `D_note`, wrong manifest scope, or altered `H_tx`.
- Note already spent.

### Concurrency, crash and recovery
- Two concurrent requests using the same challenge.
- Two concurrent requests using the same note.
- Same valid assertion and signatures submitted simultaneously to different verifier instances.
- Crash before the database commit.
- Crash after commit but before the external action.
- External action timeout with unknown outcome followed by retry.
- Duplicate outbox delivery.
- Database restore/recovery does not permit a previously consumed note to be spent again.

For each test, assert both the verifier response and the durable state transition. “One request returned success” is insufficient if the database/outbox state can still be duplicated.

## 10. OpenSK interoperability

[Google OpenSK](https://github.com/google/OpenSK) is an optional hardware authenticator target for interoperability testing. It is not a Torn Note library and is not required by the server protocol.

The expected path is:

`Browser WebAuthn API → CTAP2 authenticator (OpenSK or another key) → Java WebAuthn verifier`

No OpenSK firmware modification is required for the initial integration. The server should verify standard WebAuthn assertions and should not special-case OpenSK. Hardware tests should be added only after the normal browser/platform-passkey flow passes the V1 integration suite.

OpenSK's published installation documentation lists ECDSA P-256 support and an optional Ed25519 feature. This does not make WebAuthn a transport for Torn Note's Ed25519 note-factor signatures; those remain separate application-level proofs.

Reference: [OpenSK installation and feature documentation](https://github.com/google/OpenSK/blob/develop/docs/install.md).

## 11. Compatibility and implementation plan

Do not silently change the existing V0 Torn Note digest or manifest format.

Recommended implementation sequence:

1. Add this V1 protocol as a new, separately versioned implementation path.
2. Add JCS-compatible transaction canonicalization and cross-language test vectors.
3. Add V1 inventory-manifest scope fields and canonical note-authorization digest generation.
4. Add WebAuthn registration/assertion verification using a maintained Java library.
5. Add persistent challenge state and a transactional spend/outbox implementation.
6. Add negative, concurrency and crash-recovery tests.
7. Run browser/platform passkey tests.
8. Run OpenSK CTAP2 interoperability tests.
9. Only then consider whether the WebAuthn credential should replace the master Ed25519 identity signature in a separate profile.

Potential Java types (names are illustrative):
- `TransactionEnvelopeV1`
- `TransactionCanonicalizerV1`
- `InventoryManifestV1`
- `NoteAuthorizationEnvelopeV1`
- `WebAuthnChallengeStore`
- `WebAuthnAssertionVerifier`
- `AuthorizationSessionService`
- `TransactionalSpendStore`
- `AuthorizationOutbox`

The Java library choice and version must be checked against current maintenance status, WebAuthn Level 3 coverage, supported credential algorithms, and the project's JDK 21 baseline before adding a dependency.

## 12. Explicit non-goals and non-claims

V1 does not:
- modify OpenSK firmware;
- make the passkey directly sign the raw business transaction bytes;
- provide trusted transaction display or prove user comprehension;
- replace Torn Note's 3-of-3 Ed25519 proof profile;
- implement FROST, SNARK/ZK privacy, post-quantum signatures or EUDI compliance;
- solve compromised browser, operating system, verifier, database or authenticator firmware;
- make the current in-memory demo production-ready;
- prove that Torn Note is universally stronger than a conventional 3-of-3 authorization design.

The security claim is narrow: **provided the transaction, challenge and note bindings are correctly implemented and all proof/state checks pass, a WebAuthn assertion and Torn Note authorization issued for different transaction contexts cannot be combined to authorize the other context.** This claim requires the adversarial tests above and independent review before production use.
